# CarbonCalculator accounts and ownership contract

Status: selected product design, 2026-10-17. The owner selected verified email/password accounts and private server-saved projects across devices, and confirmed PostgreSQL storage. Product implementation and live deployment have not started. This document owns the product-specific authentication, authorization, persistence and lifecycle rules; [FeatureSpecification.md](FeatureSpecification.md) owns calculator behavior.

## 1. Simple explanation and inherited foundation

A person registers, confirms their email and signs in. They create private projects, add deliveries and documents, calculate and export reports, and reopen the same saved work on another device. Another signed-in person cannot see or modify that work. A project is a database record owned by one account, not a browser folder or a public link.

Reuse the completed template account foundation described in [Accounts](../../../docs/Accounts.md), not a new authentication implementation. The foundation and its review fixes are integrated through `45aa44308340285e54568a5a2262bcf0a6deec17` ([review PR #330](https://github.com/Grumlebob/BlazorAutoAppTemplate/pull/330), [successful exact-main CI](https://github.com/Grumlebob/BlazorAutoAppTemplate/actions/runs/38959480267)). P01 must choose a successful newer baseline containing that commit. Template completion does not prove CarbonCalculator's ownership endpoints, cleanup, production email or deployment.

Retain ASP.NET Core Identity, same-origin app cookies, the React account/session components, antiforgery, per-request session revocation, encrypted PostgreSQL mail outbox and PostgreSQL Data Protection key store. Keep the existing password/cookie/rate-limit policy and recovery behavior; link its canonical guide rather than fork a second policy here. Accounts are disabled by default in the template; CarbonCalculator explicitly enables and validates them. A product release must fail its gate if accounts are disabled or misconfigured.

Each cloned product has separate accounts, database access, stable application identity, host-only cookies and wrapping keys. Do not copy template users, demo seeds, credentials or another app's key ring. No shared SSO, organizations, collaborators, public sharing or administrator access to everyone's projects. An inherited `Admin` role alone grants no project bypass. React MFA, passkeys and external sign-in remain outside v1; remove only unused UI/integrations after dependency review, without weakening retained authentication or silently bypassing unsupported credentials.

## 2. Access matrix and account journey

| Surface | Signed out | Signed in as owner | Signed in as another user |
| --- | --- | --- | --- |
| SPA shell, About/Privacy, safe capabilities, approved catalogs | Public, no private state | Public | Public |
| Register/confirm/resend/forgot/reset | Inherited generic account flows and quotas | Inherited account behavior | Inherited account behavior |
| Project lists/CRUD and saved deliveries | 401 JSON | Own records only | Lists omit foreign rows; foreign IDs return 404 |
| Address search, route search and calculation | 401 JSON | Allowed within user/global budgets | Own inputs/results only |
| Reports, aggregation, attachments, project export/import | 401 JSON | Authorized project/record graph only | 404 for inaccessible IDs, including guessed child IDs |
| Account profile/export/delete, password/email change/logout | Inherited session/current-password rules | Current account only | Never another account |

The frontend reads `/api/client-config` and `/api/auth/session` using the existing account controller. Keep `/api/auth/*` and `/auth/*`; do not create duplicate product login endpoints. The product capabilities endpoint adds domain availability, not a competing session protocol. Private APIs return JSON 401/403 rather than redirects; authenticated requests for foreign or missing objects return the same 404 shape. Validate antiforgery on every cookie-authenticated product write, including multipart uploads and expensive search/calculation POSTs. Restrict origin/CORS through the existing same-origin policy; GETs must not create private resources or call a paid/budgeted provider.

Signed-out private navigation offers Sign in/Create account and an allowlisted same-origin return path, never private fields or tokens in a URL. After confirmation and sign-in, first use shows the approved empty Create project flow. The header adds a compact account menu for account management and Sign out; it does not introduce a new calculator navigation hierarchy. Confirmation/recovery/email-change tokens use the inherited fragment handling and are removed after consumption. Confirmation alone does not fabricate a signed-in session.

Session checking/unavailable hides private data and disables writes. Logout, expiry, password reset/change, confirmed email change and account deletion follow inherited revocation rules. Cancel old requests and clear private query caches on app/account changes. Scope query keys to `(applicationId, userId, projectId, resource)` and reject late responses from another session generation. Do not persist private queries, tokens, drafts or documents in localStorage/IndexedDB or a service-worker cache.

An unsaved edit buffer may remain in memory for the original application/account while reauthentication occurs. Bind it to that identity, hide its private contents from another account, and require explicit discard before the new account can replace/edit it. Resume only when the original account returns; never auto-submit after login. Reset delete confirmations and sensitive account form inputs across owner/application changes. Cross-tab session notification is advisory; server authorization and revision checks remain authoritative. Offline work is an unsaved in-memory buffer, not a successful server save or promised offline application.

## 3. PostgreSQL model and server ownership

Use the inherited PostgreSQL EF Core context, migration pipeline and transaction/retry conventions for Identity and product entities. Keep Redis and its supported runtime/cache uses; removing it is a separately justified product change. Do not add SQLite, a second account database, generic repository framework or browser persistence mode. Catalogs/factors remain reviewed versioned files.

| Proposed table | Ownership and invariants |
| --- | --- |
| `Projects` | Opaque ID, required string `OwnerUserId` FK to the existing `AspNetUsers.Id`, name/site/context, UTC timestamps and explicit revision. Index owner plus list order. `OwnerUserId` is immutable through normal CRUD and assigned from the session, never a writable DTO field. |
| `DeliveryRecords` | Required project FK, stable ID, revision, original editable inputs, context and selected assessment references. Validate project ownership on every operation. |
| `CalculationSnapshots` | Owner binding; optional project/delivery FKs for standalone route exploration; immutable original UTF-8 payload/hash, fingerprints and method/data revisions. Saved report links cannot point outside their project/owner. |
| `Attachments` | Required delivery FK, generated storage ID, display name, validated type/length/hash, lifecycle state and timestamps. Authorization traverses delivery to project to user. No public URL or filesystem path in DTOs. |
| Route/cache/budget records | Short-lived owner-bound route envelopes; bounded shared provider cache hidden behind authorized handlers; persisted provider-wide and per-user accounting. Cache possession/hash is never authorization. |
| Upload staging, deletion jobs and idempotency receipts | Minimal app-owned metadata for recoverable file promotion/deletion and retry outcomes. Scope receipts to user/project/operation and bind their input hash. |

Concrete entity names may follow baseline conventions. Do not store one opaque project JSON document as a substitute for required relational ownership, foreign keys and concurrency. Small typed payloads/JSON for immutable snapshots or variable domain details are acceptable. Avoid duplicated owner fields on every child unless a measured query/security requirement justifies them and consistency is enforced. Query filters alone are insufficient authorization: handlers constrain the owner/project graph before read, update, delete, attach, aggregate or export. Check nested IDs together, not independently. No existence/filename/hash leak through foreign IDs, duplicate checks, errors or counts.

Save incomplete projects/deliveries without calling a routing provider. A successful response means the database transaction committed. Use an explicit monotonically increasing revision/concurrency token on mutable entities, conditional atomic updates and an expected revision on mutations. Return 409 `revision_conflict` with safe reload/save-as-new guidance; never overwrite the browser's dirty buffer. A stale calculation must not become the current selected assessment after another device changes inputs. Validate owner, revision and fingerprint when attaching results. Network/provider/SMTP calls occur outside write transactions. Preserve the inherited fresh execution-strategy attempt scope and uncertain-commit verification; never blindly replay a mutation because a connection failed.

Bound duplicate submissions using a scoped idempotency key on creates, calculation/export creation, import and upload promotion. Same key plus different input gives 409; a retry after lost acknowledgement returns the verified prior outcome without another row, file or provider calculation. Replays still require current authorization and cannot resurrect deleted data. Set documented receipt expiry and safe behavior when an outcome is no longer recoverable. Finalize these wire fields in OpenAPI before implementing clients.

Initial limits: 20 projects per user, 500 deliveries per project, paged lists of at most 50, and the existing feature bounds for request bytes, routes and uploads. Enforce limits in concurrent server transactions, not only in the UI. Set global/user storage capacity before public registration. No silent truncation. Project/delivery search never calls a provider; place search is an explicit budgeted provider operation. Aggregation loads the authorized project's saved current assessments and fingerprints in C#; the browser submits project/context revisions, not trusted totals or a second signed local contribution store. Imported reports remain historical/unverified until explicit server recalculation. Do not introduce a new HMAC/signing key ring for this replaced local-storage design.

## 4. Retention, files, export and deletion

| Data | Selected lifetime |
| --- | --- |
| Saved project, deliveries, selected snapshots and finalized document originals | Retained until explicit deletion of the object, project or account, subject to visible capacity limits. No inherited 24-hour saved-data expiry. |
| Unattached standalone calculations/route envelopes and interrupted upload staging | At most 24 hours by default, with access denied once expired even if cleanup lags. Explicit save adopts a valid owned result into the project. |
| Provider caches | Up to seven days only where provider terms allow; precise payloads remain private operational data. |
| Idempotency receipts, deleted-file jobs and operational logs | Bounded, documented operational retention without credential/document content; sufficient to reconcile active retries/jobs. |
| Backups and user downloads | Separate documented backup rotation; downloaded exports cannot be recalled. Do not promise instantaneous backup erasure. |

Documents use private app-owned persistent storage outside webroot; PostgreSQL stores metadata/ownership, not public file URLs. Save an incomplete delivery before attaching its first file, with a clear Save delivery action if needed. The browser must not silently claim unsaved fields were committed. Upload stages bytes, enforces bounds/type/hash and current owner, then promotes through a recoverable metadata/file protocol. Failed or abandoned staging expires; finalized originals do not. Reserve quotas atomically across concurrent requests. Never deduplicate across accounts.

Initial file limits: PDF/JPEG/PNG only; 10 MiB/file, three files/delivery, 100 MiB/project, 1 GiB application upload budget and 20% disk reserve, with at most two active uploads per user. Capacity review may lower these configurable limits before launch. Bound image dimensions/decoded pixels and all staging bytes. Safe download with `no-store`, `nosniff` and safe content disposition is required; PDF inline preview needs proven isolation. A file attachment does not run OCR, confirm dispatch, alter quantity or certify malware safety.

Remove/delete first makes the object inaccessible through its ownership graph, commits a durable deletion job, then deletes only owned bytes and reconciles on failure/restart. Project deletion removes its delivery/report/attachment access and associated rows; account deletion removes all owned product data plus the Identity account under the existing current-password/session protections. Extend account deletion and personal-data export as part of the product lifecycle; Identity deletion alone is insufficient. Prevent a concurrent save/upload from recreating rows/files after deletion. Keep minimal deletion jobs independent of the removed user FK until physical cleanup finishes. Report historical attachment metadata can remain only while the owning report remains; remove direct access to deleted bytes. Never mutate the numerical contents of a retained snapshot to disguise unavailable originals.

Report JSON exports exact stored snapshot bytes. Project backup exports editable data and historical snapshots plus an originals manifest; ordinary JSON omits document bytes. Account export includes account data, all owned projects and document manifests, excluding password hashes, stamps, key material, mail tokens, access secrets and raw files by default. Offer originals through separate authorized downloads. Import validates bounds, creates a new project owned by the current user and fresh child IDs atomically, strips any supplied owner/access claims, and never fetches external file URLs. No import grants access to another user's records or promotes claimed calculation/source approval.

## 5. Email, deployment and recovery

P08B proves registration, confirmation, recovery, email change, revocation and the empty private-project entry using isolated PostgreSQL and the template's TLS SMTP fixture. Local evidence requires no live provider account or mail to real people. Public self-registration requires `Accounts:Enabled=true`, `Accounts:RegistrationEnabled=true`, canonical product HTTPS `Accounts:PublicOrigin`, working protected TLS SMTP settings and a verified sender. Inspect usable existing free service access before asking for missing credentials/provider interaction. Do not silently accept a paid plan, log secrets or pretend queued mail means inbox delivery.

Before public launch, record a controlled authorized real inbox delivery/confirmation/recovery check, sender-domain setup where required, free-service quotas and operational failure guidance. This is a product launch gate, not a reason to block local implementation. Provisioned-account/no-SMTP mode may support local development; it does not satisfy the selected public registration/recovery journey. A one-time optional Admin seed is disabled and cleared after provisioning; never introduce a default password.

Retain PostgreSQL migrations/bundle, readiness, protected Data Protection wrapping certificate/private key/password, encrypted outbox and supported Redis deployment. Back up product/Identity/key-store database state and finalized document bytes consistently through a tested quiesced write window or an equivalent implemented consistency protocol. Include protected app identity/key recovery inputs off-host; a database dump alone is insufficient. Restore into an isolated owned target with SMTP/provider egress disabled. Prove records, exact report bytes, original documents and ownership denials; Redis is rebuildable, not the only copy of saved user work.

Document and test the product disaster-restore session policy before exposure: invalidate restored pre-restore sessions and stale account-mail intents, require sign-in, and ensure no recovered deletion job or upload grants access to deleted data. Keep necessary wrapping keys to decrypt retained data; do not indiscriminately delete key rings. A restore may recover an earlier data point, so disclose recovery point/backup retention and reconcile known deletions before reopening service. Ordinary app restarts preserve valid sessions/data under the inherited policy. Image rollback does not undo a PostgreSQL schema migration; use compatible migrations and the retained release/restore tooling.
