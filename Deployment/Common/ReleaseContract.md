# Release Contract

`Deployment/Common/release.yml` names the application image, migration bundle, and optional prefix for the GHCR payload package. A release binds one full source SHA to a successful CI attempt triggered by `push` or `workflow_dispatch`. Main CI publishes the application image, a digest-pinned GHCR payload with the migration bundle and manifest, and a receipt from the exact successful publisher job. Pull request checks publish no release. CD requires a successful `publish-main` job on the same run attempt. LocalSingleNode's initial AgentSetup checkpoint requires a main push; later release selection also accepts manually dispatched CI.

Schema v2 `release-manifest.json` binds the repository and source SHA to the CI run ID and attempt, frontend and acceptance profile pair, registry image digest, ordered migration IDs, migration bundle SHA-256, and .NET SDK. LocalCluster and LocalSingleNode CD validate that manifest against the selected source, receipt, GHCR digest, and image labels before migration. They verify the deployed image identity after acceptance. The configured payload prefix changes only the payload package name; it does not change application image names. Legacy schema v1 is limited to verified `BlazorAuto`/`BlazorAutoV1` releases; it cannot describe React.

Cloud CD selects the same exact CI receipt and retrieves the migration bundle from GHCR. It retains exact-run Actions artifact fallback for pre-receipt CI attempts. Cloud's deployment-specific checks remain separate; follow [the Cloud deployment guide](../Cloud/HowToDeployCloud.md) for its current release and acceptance checks.

The main publisher job needs `packages: write`; repository Actions permissions must allow `GITHUB_TOKEN` to grant that job-scoped permission. Validation stays read-only. CD uses `GITHUB_TOKEN` with `packages: read`. No GitHub token goes into the vault. Manual node credentials, when needed for a private application image, need only `read:packages`.

For a new receipt, if the GHCR payload is missing or cannot be retrieved, stop. Run the full CI workflow again for the selected source SHA and deploy only after that run publishes a fresh receipt and payload. Do not rerun only the publisher job after a failed CI run. Legacy pre-receipt runs use their exact Actions artifact while it remains available; if it is missing or expired, run the full CI workflow again for the same source SHA.

## Select a published source

A documentation-only commit using `[skip ci]` creates no release. LocalCluster and LocalSingleNode can dispatch from current `main` with `target_sha` set to a full, previously published SHA on `main`; leave it empty only when the dispatched commit has its own successful publishing run. Cloud has no `target_sha` input and deploys the dispatched `main` commit. If that commit has no release, manually dispatch CI on `main` and require successful publication before Cloud CD. Do not substitute a PR payload, a legacy artifact from another run, or an ancestor's release for the selected source.
